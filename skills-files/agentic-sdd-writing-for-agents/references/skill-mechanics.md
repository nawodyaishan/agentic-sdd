# Skill mechanics and compatibility

Choose the invocation contract from actual supported harness behavior. A unique
namespaced directory ID is the portable identity; keep frontmatter aligned and
give reusable entries a precise description. User-facing convenience labels
must not overwrite unrelated installed skill IDs.

An explicit-only entry should be reached by the user's actual request. Where
supported, `disable-model-invocation: true` reduces advertisement; it is not a
security boundary. OpenCode V2 documents that hidden skills remain explicitly
loadable by ID, and metadata precedence may differ from another harness. A
loaded skill must still retain the invoking request's authority and effects.

Keep shared reference bodies in packaged ordinary files if multiple entries
need them; they need not invoke another user-only skill to read a contract.
An alias can point to the reusable procedure without spawning a fresh agent.
Descriptions/pointers are context cost; create a separately advertised entry
only when its independent trigger earns that cost.

Before packaging, verify supported frontmatter, unique IDs, relative reference
closure and applicable license notices. Do not assume a slash-command alias,
plugin, automatic dispatch rule or another adapter exists merely because a
source skill uses it. Availability and permissions must be stated separately.
