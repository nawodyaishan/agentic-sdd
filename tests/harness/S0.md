# S0 offline transport boundary

Scope/authority: [feature 004 approval](../../specs/004-vnext-harness/spec.md#approval),
[T11 proposal and S0 contract](../../specs/004-vnext-harness/plan.md#s0-implementation-contract-authorized-2026-10-31).
This is optional evaluation code, not an installed proxy/plugin, provider adapter,
model launcher or approval ledger. No real endpoint or credential route is supported.

## Run

```sh
TMPDIR=/tmp/opencode python3 -B -m unittest discover -s tests/harness -p test_offline_transport.py
python3 -B tests/harness/s0-fixtures.py
```

The first command exercises pure budget state without HTTP; container-only tests
are explicitly skipped, not passed. The second runs budget/HTTP tests, native
fake-response construction, affected native compatibility probes, then a separate
worker. It requires local Docker, the preloaded pinned Python image and the
explicitly selected existing OpenCode **2.2.5** binary. Nothing is installed or
pulled. `OPENCODE_TEST_BINARY` may name a reviewed binary; version mismatch fails.
`--case <budget-http|native-shape|native-compat|separate-worker>` is a partial
diagnostic selection, never full coverage. `--output` must be new/empty, external,
private and non-symlink; default is `/tmp/opencode/sdd-s0.<random>/`.

`offline-s0-checks.json` exposes the full command as focused `s0-offline-boundary`.
The Go runner checks executable/Docker prerequisites; the fixture checks the exact
image/version itself without downloads. Observe both levels; a blocked/failed
fixture is not a native success just because its contract is schema-valid.

## What is enforced offline

- Fixed numeric loopback upstream, exact chat-completions path/model, strict
  bounded JSON field allowlist, text-only messages, one explicit output-cap field
  (`max_tokens` **or** `max_completion_tokens`). No route/model/body overrides,
  redirects, WebSocket/CONNECT, ambiguous framing or forwarded caller headers.
- Locked cumulative reservations across clients/sessions, with input bytes and
  the entire requested output byte capacity reserved before dispatch. No refund
  after upstream failure; denied or uncapped requests never reach the fake
  endpoint. No usage-response accounting is trusted to release allowance.
- Metadata-only owner-private fsynced journal before send; reopening an existing
  allocation is refused after restart. Journal loss/change, cancellation,
  expiry, oversized response or uncertain upstream behavior stops forwarding.
  Journal re-creation under a different path is **not** an authority mechanism;
  offline callers are trusted to select one allocation. Online allocation
  provenance/restart reconciliation remains unimplemented.
- Bounded request/response sizes and per-read plus absolute deadlines. Buffered
  fake SSE is bounded, not certified online streaming. Cancellation prevents new
  admissions and withholds later output; an admitted send may have reached the
  fake upstream before cancellation, keeps its reservation, and is not undone.

All runtime containers are unprivileged, read-only-root, network-none, capability
dropped, no-new-privileges and resource-bounded. Only reviewed fixture modules,
native binary/templates and dedicated synthetic inputs are mounted read-only.
No host home, native auth database, primary service or Docker socket is mounted.
The trusted host driver records logs and removes only its own CID-identified
containers. A separate network-none worker sees only its input/probe, not native
runtime/gate state, headers or sockets. This is observed offline separation, not
a VM, shared-kernel escape defense or real native-shell isolation guarantee.

## Native details and remaining gates

The restart exposed **2.2.5** rather than reviewed 2.2.0. User allowed versions
above 2.2.0; this fixture freezes the actual 2.2.5 binary/hash instead of claiming
compatibility for an entire range. The existing B3 probe still defaults to 2.2.0;
only this driver explicitly selects 2.2.5 for revalidation. Native template and
product support pin remain unchanged; old observations are not relabelled current.

Official [V2 policies](https://opencode.ai/v2/docs/policies), consulted 2026-10-31,
describe a 2.2.3+ meaning change: bare `integration.use: "*"` now controls provider
integrations, while MCP/skills/plugins have separate actions. In the **synthetic
S0 config only**, the fake integration gets a narrow explicit allow and those
three extension types remain denied. No real provider is enabled. Historical
prefixed B3 statements are exercised separately for compatibility, not assumed.

Native request construction uses a **custom fake provider** with the selected
model's wire ID and synthetic key, not the real `opencode/` endpoint. Fake text
and bounded SSE prove actual client → gate → fake HTTP → native response flow;
they do not prove DeepSeek tool capability, selection, actual billing, privacy
or native lifecycle obedience. Any observed cap-less auxiliary request is denied,
not repaired, retried upstream or treated as a safe completed generation.

**S0-F1:** accounting is UTF-8 bytes, not real DeepSeek tokens. A request's cap
field supplies an offline byte reservation only; missing/ambiguous caps fail.
Tokenization/output reasoning limits must be independently verified for S1.
**S0-F2:** online egress/credential isolation, all auxiliary native routes,
real endpoint access and authoritative allocation provenance are not certified.
The six-request real preflight was later **conditionally authorized** in
spec §Approval; these byte-only tests do not satisfy its real-token/online
conditions, and no real request has run. No external
tokenizer, auth copy, endpoint probe, model fallback or network relaxation occurs
to make this fixture pass. B3/B5/B6/B7/B8 findings remain in force.

Only private generated fixture logs/metadata are retained under the printed output.
Keep raw logs seven days and sanitized observations thirty days by default,
with user-controlled cleanup. Failed development attempts remain evidence, not
passing native samples. Full feature acceptance remains in
[the acceptance map](../../harness/acceptance.md) and current task continuation.
